AI Search in PLM · Explanation System

Designing for Match Reasons

A system-level approach to explaining search results across all match types — from keyword hits to semantic understanding to visual similarity.

Design Philosophy

Show real values. Show the connection. Let users verify.
In enterprise search, trust comes from auditability — not AI confidence scores or generated summaries. Every match reason the system surfaces must be traceable to actual data in the record. The AI's role is to surface and connect, not to conclude on the user's behalf.

Paradigm A — Text Bridge Show query term → connection type → matched value → location
Keyword Keyword Match Text bridge always showable ▾
Definition

User provided a word or phrase. System found the exact word(s) in the record's node name or a configured keyword-searchable attribute. The match may be direct on the record, or found via a related object (e.g. a Style matched because its linked Colorway contains the word).

Semantic Semantic Match Text bridge sometimes showable ▾
Definition

User provided a word or phrase. System found meaning-equivalent content in a semantically-indexed attribute. The bridge between query and result is sometimes explicit (synonym-level) and sometimes implicit (holistic match where no single word pairs up). Only operates on attributes configured by the admin as semantically searchable. The match may be direct on the record, or found via a related object.

Whether the match is direct or via a related object, the chip shows the related object name as the location. The relationship detail doesn't need to be surfaced in the chip.

Paradigm B — Visual Evidence Show matched image thumbnails as evidence; user verifies visually
Image 1 Image Match — Text to Image Text query → visually similar images in records ▾
Definition

User provided a word or phrase. System found records whose attached images are visually similar to the meaning of the query. No text bridge exists — the evidence is the matched image(s) themselves. The query is treated as a whole (e.g. "red summer dress" finds images that look like a red summer dress, not images that are red + summery + dress-shaped separately).

Conversation Conversation Match Query → matching content inside a conversation ▾
Definition

User provided a query. System found matching content inside a conversation associated with a record. Bridge is a passage from the conversation. Distinct from document match in that conversations carry speaker and time context — who said it and when is part of the evidence. Keyword matching recommended as the starting point.

Chip Explosion Rules

Group 1
Same term, multiple locations on the same record
Deduplication — collapse multiple signals about the same query term into one primary chip
Rules
1
Collect all matches for each query term
Gather every keyword and semantic match across all searchable attributes for that term.
2
Order by match type first, then by attribute rank
Keyword matches rank above semantic matches. Within each group, rank by attribute priority (admin-configured at MVP). Keyword always wins over semantic for the same term — don't show both.
3
Show top-ranked match as primary chip
The highest-ranked match for that query term becomes the visible chip. All remaining matches — including other colorway values, other attributes, semantic matches — go behind a +X control.
4
Group by query term, not by display value
The +X groups everything that matched because of the same query term — even if the found values look different (Dark Red, Light Red, Red, coral tones). Intent is the anchor, not the display text.
Concrete Example — Query: "red", on a single Style result
All matches collected (unordered)
keyword Dark Red in Colorway
keyword Light Red in Colorway
keyword Brick Red in Colorway
keyword Red in Material Name
semantic "Red" ≈ coral tones in Description
What renders on the card
Chip row on result card:
Dark Red in Colorway +4
Expanded (+4):
Light Red in Colorway Brick Red in Colorway Red in Material Name "Red" ≈ coral tones in Description
All 5 matches grouped under the query term "red" — regardless of the different found values. Keyword matches first, semantic last.
Group 2
Same term, multiple match paradigms
When a single query term produces matches across different paradigms — show the highest-ranking one only
Core Principle

For any query term, show one chip from the highest-ranking paradigm that produced a match. Suppress everything below it. Lower-paradigm matches go into +X alongside the Group 1 overflow. The user always gets one clear answer to "why did this appear" — not multiple competing explanations for the same term.

Paradigm Hierarchy — Text Queries
1
Text Bridge — keyword first, semantic second
Most authoritative. Match is on structured record data — directly verifiable by the user.
2
Visual Evidence — if no text bridge
Match is on images attached to the record. User verifies visually. Strong but less precise than structured data.
3
Document — if no text bridge and no visual
Match found inside an attached reference document. Supplementary — the record's core data doesn't confirm the match.
4
Conversation — last resort fallback only
Match found in a conversation thread. Weakest signal — incidental mention rather than deliberate data. Only surfaces when nothing stronger exists.
Special Rule — Image Queries

When the user's query is an uploaded image, show visual chips only. Text bridge, document, and conversation matches are suppressed entirely. Image search has a distinct mental model — the user is asking "find things that look like this," not "find records that mention this." Surfacing document or conversation matches on an image query breaks that expectation.

Decision Table — What to Show
Text bridge Visual Document Conversation Show
✓ any any any Text bridge chip only
✗ ✓ any any Visual chip only
✗ ✗ ✓ any Document chip only
✗ ✗ ✗ ✓ Conversation chip only

Lower-paradigm matches don't disappear — they fold into the +X alongside Group 1 overflow. Discoverable, but not competing for attention.

All paradigm matches found
